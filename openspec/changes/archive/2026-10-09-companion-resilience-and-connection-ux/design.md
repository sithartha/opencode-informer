# Design

## Context

See proposal.md - Why. Current state relevant to the approach:

- `plugin/src/activity.js` reduces each form field's options to labels only
  (`fieldOptions`), and `form.created` sets `session.lastActivity` to the question title.
- `plugin/src/pairing.js` issues tokens after the helper approves; `POST /pair` in
  `plugin/src/server.js` is unauthenticated and only the loopback decision endpoint is
  restricted.
- The app stores only the bearer token and the Mac name (`secureTokenStore`), discovers
  through BLE, and `establish()` reuses a token or pairs (`app/src/useBridge.ts`).
- `app/App.tsx` renders the manual `host:port` input inline; `SessionCard` shows
  `session.title || session.cwd`; question options are `string[]` end to end.

## Goals / Non-Goals

**Goals:**

- Make the idle termination observable and remove known unhandled-failure paths.
- Stop the question title from replacing a message the user is reading.
- Carry and render question option descriptions.
- Reduce connection friction: remembered computer, clearer manual dialog.
- Require a Mac-shown code plus attempt limiting on the LAN pairing path.

**Non-Goals:**

- No redesign of BLE discovery or the doorbell.
- No server, no new runtime dependency, no crash-reporting service.
- Not a full conversation transcript: only the activity text before a pending question is
  preserved; earlier history is not.
- Not adding certificates/mTLS or an IP allowlist as the access-control mechanism.
- Building to the phone is a task, not part of this plan.

## Decisions

### Option objects on the wire; answers send the option value

- **Choice**: question options become `{ label, value?, description? }` in the snapshot and
  the `question.asked` event. The app sends the option's `value` when present, else its
  `label`; `buildFormAnswer` already matches label or value, so answers keep working.
- **Why**: descriptions exist upstream and are dropped today; label+value+description is
  the minimum to render them and still answer reliably.
- **Alternatives**: a parallel `optionDescriptions: string[]` (fragile index alignment);
  a description map keyed by label (collides when labels repeat).

### Preserve activity text while a question is pending (bridge is authoritative)

- **Choice**: `form.created` no longer writes the question title into `session.lastActivity`;
  while a session has a pending question, `session.text.ended` appends
  (`existing + "\n\n" + new`) instead of replacing; `markResolved` drops the pending entry
  so normal replacement resumes. Appends are capped to a generous length so payloads stay
  bounded.
- **Why**: the overwrite happens in the bridge model and is re-applied on every snapshot, so
  fixing it only in the app would regress on reconnect.
- **Alternatives**: a separate "question title" field on the session (more contract churn);
  app-only fix (rejected above).

### Pairing code generated by the bridge, displayed by the helper

- **Choice**: `PairingManager` generates a short numeric code, exposes the current one, and
  includes it only in the approval signal to the helper
  (`onApprovalRequested` → doorbell `{ kind: "pairing", ..., code }`). `POST /pair` requires
  a matching, current code before `pairing.begin`. Failures are counted per remote address
  over a rolling window, with a temporary lockout. The helper displays the code; it never
  forwards it to the client.
- **Why**: the code proves a human at the Mac authorized that specific device, and keeping
  it out of every client-bound payload means a LAN listener cannot learn it. Rate limiting
  plus lockout stops prompt spam and brute force.
- **Alternatives**: mTLS/certificates (heavy provisioning); a LAN IP allowlist (brittle on
  changing Wi-Fi); a code only for manual connections (leaves the shared `/pair` endpoint
  brute-forceable).

### Remember the last computer and try it first

- **Choice**: persist the bridge `host`/`port` in SecureStore next to the token. On launch
  and on foreground while unpaired, if a token exists, try the remembered address with a
  short timeout first; on success, stream; on failure, fall through to BLE discovery and
  then manual entry. Clear the remembered address on `401` (revoked token).
- **Why**: avoids a slow or absent BLE scan on every launch while keeping the existing
  fallback path.
- **Alternatives**: store the whole base URL (parse on read - equivalent churn); store
  multiple Macs (v1 pairs with one).

### Manual connection in a dialog

- **Choice**: a `ManualConnectModal` (same style as `SwitcherModal`/`ConfirmModal`) opened
  from the connect block, with separate address and port fields, an explanation of when to
  use it, and validation by joining through `parseRendezvous`/`manualBase` before
  `connectManual`.
- **Why**: two labeled fields avoid `host:port` parsing confusion and satisfy the request.
- **Alternatives**: keep the inline field with two inputs (still clutter); single field
  with a better placeholder (the current behavior, rejected).

### Lower-latency updates

- **Choice**: cut the bridge's out-of-band title/cost refresh debounce from 1200 ms to
  250 ms, the new-session idle reflection from 900 ms to 300 ms, and the app's snapshot
  resync throttle from 1000 ms to 400 ms; the question/activity stream stays push-based.
- **Why**: the visible 1-2 s lag was these debounces/throttle, not the SSE stream (which
  delivers immediately).
- **Alternatives**: none needed; the values are tunable trade-offs between latency and
  request volume.

### Recent activity history on the card

- **Choice**: the app keeps the last three activity messages (splitting the bridge's
  `\n\n`-joined text), renders each as its own nested card, shows the latest by default,
  reveals the earlier cards behind a control, and opens a message in full in a modal on tap;
  when a question is pending it shows the recent cards by default.
- **Why**: the text was being clipped with no reliable way to read it; cards plus a
  full-message modal make long messages readable and keep the glance compact.
- **Alternatives**: an inline "more/less" expander (still clipped inside the card); append
  everything into one string (unbounded and hard to read).

### Directory name and option descriptions in the UI

- **Choice**: a small `dirName(cwd)` helper (split on `/` and `\`, drop trailing
  separators) feeds the session header. An option renders as a button holding only its
  label, with its description below the button (not inside it); both wrap when long.
- **Why**: no contract change for the directory name (the snapshot already has `cwd`), and
  the description UI reuses existing components.
- **Alternatives**: a precomputed name from the bridge (contract churn for a display detail).

### Session cost (spent)

- **Choice**: extend the out-of-band session lookup the bridge already performs for titles
  to also return the session's accumulated `cost`, refresh it at turn end, carry it as an
  optional `cost` field in the snapshot plus a `session.cost` event, and render it as a
  distinct `$0.0123` chip (amount and currency, no label word) beside the agent chip.
- **Why**: OpenCode already tracks a per-session cost, so no new data source is needed -
  only the existing `ctx.session.get` lookup extended and a field threaded through.
- **Alternatives**: a dedicated cost-polling endpoint (more churn for the same data);
  showing token counts instead (not what was asked).

### Idle diagnostics in local storage

- **Choice**: `app/src/diagnostics.ts` stores a small JSON blob in SecureStore
  (`lastTransition`, `lastConnection`, `lastError`, `backgroundedAt`, `foregroundedAt`).
  It tracks AppState transitions; on cold start, a recorded `backgroundedAt` with no later
  `foregroundedAt` is reported as "may have ended in the background". A global handler
  (`ErrorUtils.setGlobalHandler`) records uncaught JS errors and chains the previous
  handler. Notification-scheduling and reconnect calls are wrapped so a failure records a
  breadcrumb instead of escaping. Settings shows the latest diagnostic.
- **Why**: it makes the opaque termination observable with the storage and error hooks
  already present; no new dependency.
- **Alternatives**: `expo-file-system` (new dependency); a hosted crash reporter (network,
  privacy, heavy); no diagnostics (rejected by the user).

## Risks / Trade-offs

- [Wire break for options] → bump `contract.version`, update fixtures/tests, ship app and
  plugin together; the app renders an option as its label when it receives a plain string,
  so a mismatched pair degrades instead of breaking.
- [Pairing-code friction] → shown once per device and only when no pairing is pending;
  tokens persist, so re-pairing is rare.
- [Activity text can grow while a question is pending] → capped appended length keeps the
  card and notification payload bounded.
- [A force-quit looks like a background termination] → phrase the diagnostic as "may have
  ended in the background" and keep the raw breadcrumb.
- [Remembered address goes stale after a network change] → short timeout then fall back to
  BLE/manual; clear on `401`.
- [Diagnostics privacy] → stored locally only, truncated strings, never transmitted.

## Migration Plan

- Bump `contract.version`; bump the plugin entry version so OpenCode re-imports the module
  graph.
- New SecureStore keys are additive; absent keys fall back to today's behavior, so no data
  migration is needed.
- Rollback: revert the change; the app's string-tolerant option rendering keeps an old app
  usable against the new bridge.

## Open Questions

- Exact code length/rotation and lockout thresholds are tunable defaults (proposed: 6
  digits; 5 failures in 5 minutes → 15-minute lockout). They do not change the specs.
