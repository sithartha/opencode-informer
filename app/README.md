# OpenCode Informer

Expo + React Native client (iOS first, Android where feasible) for the OpenCode
mobile bridge. It discovers and pairs with the Mac helper over BLE, receives agent
activity over the LAN, raises actionable notifications, and sends approvals back.

## How it works

```
BLE (discovery + wake)                 WiFi (data)
  Mac helper  <---- connect ---->  app  <---- SSE /events ---->  plugin bridge
       |  rendezvous: host:port         --- POST /resolution --->  bridge
       |  doorbell (notify)             --- GET /state --------->  bridge
```

- **Pairing**: BLE connect -> read rendezvous `host:port` -> `POST /pair` -> the Mac
  user approves in the helper -> poll -> store token in SecureStore.
- **Live view**: SSE `/events` updates the dashboard; `/state` seeds it.
- **Notifications**: permission/question/completion events become local notifications
  with actions; tapping an action posts a resolution.
- **Background wake**: a BLE doorbell wakes the app, which refetches state and raises
  a notification. The SSE stream is not alive while suspended.

## Requirements

- macOS 14+ with the bridge and helper running
- Node 20+, Xcode with an iOS simulator
- A **development build** (Expo Go cannot provide BLE or local-network config)

## Setup

```bash
cd app
npm install
npm run prebuild        # writes ios/ and android/ (already committed here)
npm run ios             # build and launch on the iOS simulator
```

The first `prebuild` already generated `ios/` and `android/`. If you change
`app.json`, re-run `npm run prebuild`.

## Native configuration (app.json)

| Setting | Purpose |
|---|---|
| `ios.infoPlist.UIBackgroundModes` = `["bluetooth-central"]` | wake on BLE in the background |
| `ios.infoPlist.NSBluetoothAlwaysUsageDescription` | Bluetooth permission text |
| `ios.infoPlist.NSLocalNetworkUsageDescription` | local network permission text |
| `ios.infoPlist.NSAppTransportSecurity.NSAllowsLocalNetworking` | allow plain HTTP to the Mac |
| `android.permissions` (BLUETOOTH_*, POST_NOTIFICATIONS, FOREGROUND_SERVICE, ACCESS_FINE_LOCATION) | Android BLE, notifications, service |
| `expo-build-properties` `android.usesCleartextTraffic` | allow plain HTTP on Android |

Verify the iOS keys with:

```bash
plutil -p ios/OpenCodeInformer/Info.plist | grep -iE "Bluetooth|LocalNetwork|BackgroundModes|AppTransport"
```

## Lock Screen activity (Live Activity)

The app shows an iOS Live Activity on the Lock Screen (and Dynamic Island) with the
aggregate agent state: total active sessions and a breakdown of working /
waiting-for-approval / waiting-for-answer, prefixed with `!` when something needs you.

- **Start/update/end**: it starts when the first active session appears, updates as the
  aggregate changes, and ends when no sessions remain.
- **Updates**: while the app is foreground, from the SSE stream; while backgrounded,
  from each BLE doorbell wake (the app refetches `/state` and updates).
- **Staleness**: between wakes it holds the last snapshot; if a refresh fails or the
  aggregate has not been refreshed for five minutes, the subtitle is marked `stale`.
  Continuous updates between wakes would need the APNs push-to-update path (not in v1).
- **Mark**: the "OI" white-on-black mark, generated by `scripts/make-brand-assets.swift`
  (also the app icon).
- **Opt-out**: the "Lock Screen activity" switch in the app ends the activity and stops
  new ones.

### Android

Android has no Lock Screen Live Activity. The comparable surface is an **ongoing
notification** with the same aggregate. A truly persistent ongoing notification requires
an Android **foreground service**, which is not implemented yet; on Android the summary is
best-effort while the app is alive. This is a known gap, tracked in the change tasks.

## Session detail

The dashboard lists one card per active session:

- the phase (working / waiting for approval / waiting for answer / completed), the current tool, the number of subagents, and the number of active shells;
- the session's **agent (mode)** and **model**, e.g. `build · deepseek/deepseek-flash` (from the `session.updated` stream event);
- a compact summary of the session's latest activity (`lastActivity`, updated live by the `session.activity` stream event); http(s) URLs in the text are tappable and open in the browser;
- any pending permission or question for that session, inline, with Allow / Deny or the question's options (at most one pending per session; a new request supersedes the previous).

Controls on each card:

- **+** beside the hero count starts a new, empty OpenCode session (then type its first prompt in the card);
- **Stop** on a running card asks for confirmation, then stops the current turn and leaves the session inactive with a prompt field (`POST /stop`);
- **×** (top-right) asks for confirmation, then closes the session (`POST /close`);
- tapping the agent/model chip opens a picker populated from `GET /options` (the modes and models OpenCode reports — arbitrary and configurable), and switching applies via `POST /switch`.

Pending requests are reconstructed from `GET /state` (the snapshot includes them), so a session that was already waiting when the app was closed still shows its pending request after a reconnect or a doorbell wake.

When pairing, the app sends a device name — the system name by default, editable via the **Device name** field — so the Mac helper's approval prompt reads "Pair &lt;device name&gt;?".

## Troubleshooting

**`pod install` stalls downloading React Native artifacts** (hangs on
`repo1.maven.org`, ~0.5 KB/s). React Native supports a Maven mirror via the
`ENTERPRISE_REPOSITORY` environment variable; the mirror must have the same layout
as Maven Central. For example:

```bash
ENTERPRISE_REPOSITORY=https://maven.aliyun.com/repository/public npx pod-install
```

The downloaded tarballs live under `ios/Pods/ReactNativeCore-artifacts`,
`ReactNativeDependencies-artifacts`, and `hermes-engine-artifacts`; a valid tarball
is skipped on the next run.

**App crashes at launch with `UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`.**
iOS 27 asserts unless the app adopts the UIScene life cycle. `expo prebuild` generates the
legacy (non-scene) `AppDelegate`; `plugins/withSceneLifecycle.js` rewrites it to use Expo's
`ExpoAppSceneDelegate` and adds `UIApplicationSceneManifest` to `Info.plist`. Change those
in the plugin, then re-run `npm run prebuild` — do not hand-edit the generated `ios/` files.

**Headless verification without BLE or the dev launcher.** Set `EXPO_PUBLIC_DEV_HOST=host:port`
to make the app skip BLE and connect straight over HTTP, and build a Release app that embeds
the bundle:
```bash
cd ios && EXPO_PUBLIC_DEV_HOST=127.0.0.1:38963 xcodebuild \
  -workspace OpenCodeInformer.xcworkspace -scheme OpenCodeInformer -configuration Release \
  -sdk iphonesimulator -destination 'platform=iOS Simulator,name=iPhone 17' \
  -derivedDataPath build/DerivedData CODE_SIGNING_ALLOWED=NO build
```
A Release build starts deterministically (no Metro, no dev launcher), which is convenient for
CI and simulator checks.

## Known limitations

- **iOS force-quit** stops BLE wakes until the app is reopened.
- **Live Activity across a force-quit** can't be ended by the next launch (`expo-live-activity` doesn't expose enumerating existing activities); it refreshes on the next update or when iOS ends it.
- **BLE range** is about 10 m; out-of-range notification needs a future APNs path.
- **OpenCode-only**: other agents are not covered in v1.
- Replies require the phone and Mac on the same LAN.
- Android support is scaffolded but not yet device-verified.
